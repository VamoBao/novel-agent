# Git 提交规范

## 1. 核心原则：原子性与一致性

本文档在**执行提交任务前**读取——无论是用户显式下达提交指令（如「提交刚才的修改」），还是工作流在需求完成后自动提交，均遵循以下规范。

在Agent工作流中，Git 不仅仅是版本控制工具，更是**系统状态的锚点**。每一次 Commit 都必须是一个完整、独立、可回滚的“逻辑事务”。

- **原子性**：一次提交只包含一个逻辑功能或修复。禁止将多个不相关的需求或 Bug 修复混入同一个 Commit。
- **一致性**：代码修改与文档更新（`ARCHITECTURE.md`、`PROGRESS.md`；若本次修改涉及目录或模块结构变动，还包括 `AGENTS.md`）必须在同一次 Commit 中落盘。禁止出现“代码提交了但文档没更新”的中间状态。

## 2. 提交信息格式

采用结构化的 Conventional Commits 规范，以便于Agent解析和生成后续的版本日志。

```text
<type>(<scope>): <subject>

<body>

<footer>
```

### 2.1 字段说明

- **`type`** (必须)：提交类型，限定为以下枚举值：
  - `feat`: 新功能
  - `fix`: 修复 Bug
  - `refactor`: 代码重构（不改变外部行为）
  - `perf`: 性能优化
  - `docs`: 仅文档更新
  - `test`: 增加/修改测试用例
  - `chore`: 构建工具、依赖变动等杂项
- **`scope`**（有明确模块划分时必须）：影响的模块名称。取 `ARCHITECTURE.md` 分层结构中的实际目录名（如 `workflows`、`state`、`tools`），使用小写及中划线；影响面为全项目或无明确单一模块时可省略（如纯文档同步、根目录配置变动）。
- **`subject`** (必须)：简明扼要的动作描述，使用祈使句（如“添加导出功能”而非“添加了导出功能”），不超过 50 个字符。
- **`body`** (可选)：详细说明“做了什么”及“为什么这么做”。如果有关联的验收标准 (AC)，需在此列出。
- **`footer`** (可选)：关联的 Issue 编号或破坏性变更说明。

## 3. 提交内容约束

- **禁止提交报错代码**：在执行 `git add` 前，必须确保 `bun run typecheck`、`bun run lint` 及 `bun run test` 100% 通过。
- **禁止提交非必要文件**：不得提交 `node_modules`、构建产物、本地环境配置文件（如 `.env`，本项目已 gitignore）、本地参考资料目录（`files/`）及 IDE 配置文件。
- **代码与文档强绑定**：如果本次修改改变了模块结构或业务逻辑，必须在本次提交中包含对 `ARCHITECTURE.md` 和 `PROGRESS.md` 的更新；若涉及目录或模块结构变动，还须包含 `AGENTS.md` 的同步更新。

## 4. 示例

### ✅ 优秀的提交示例

**示例 1：新功能开发**

```text
feat(agents): runReactAgent 增加流式输出能力

- 在 src/agents/react.ts 中新增 runStream 接口，支持逐 token 回调
- 新增中断处理，用户取消时正确清理未完成请求
- 满足 AC: 长文本生成过程中可随时中断且不残留状态

Refs: #102
```

**示例 2：Bug 修复**

```text
fix(tools): 修复工具调用结果为空时 Agent 循环崩溃的问题

- 原因：未校验工具返回值为 undefined 即直接读取字段
- 修复：增加空值守卫并补充边界用例测试

Closes: #118
```

### ❌ 糟糕的提交示例

```text
update
```

*错误原因：无类型、无模块、无具体描述，Agent无法解析。*

```text
feat: 修改了 Agent 循环和工具注册表，顺便修了配置加载的 bug
```

*错误原因：违反原子性原则，将多个不相关的修改混入一次提交。*

```text
fix(agents): 修复了消息历史丢失问题
```

*错误原因：仅修改了代码，但没有同步更新 PROGRESS.md 中的已知 Bug 记录，违反一致性原则。*
