# 需求指南

## 概述

- 用户提供的需求可能是模糊不完整的，需要对需求进行拆解评审，通过推荐或者用户回答的方式来完善需求的细节
- 需求先分级：**简单需求**走快速通道，作为单一任务直接执行；**复杂需求**必须先做任务拆解，形成任务清单落盘 `PROGRESS.md`，再以 WIP = 1 逐任务执行——每完成一个拆解任务立即更新其状态，全部拆解任务完成后将清单归一为一条需求完成记录

## 需求完整性与可行性校验指引

### 1. 核心原则：不盲从，先对齐

当用户在 CLI 中提出修改或新需求时，**严禁**立即开始编写代码。你必须首先完成**需求分级**（见第 2 节），再作为“需求分析师”对用户输入的意图进行解构与校验。
简单需求可跳过结构化提问与任务包确认，但仍需在内部完成范围与验收检查；如果需求存在模糊、遗漏或执行风险，你必须向用户发起**结构化提问**，直到需求满足完整的交付标准后，方可进入开发阶段。

### 2. 需求分级：简单需求与复杂需求 [重要]

接收需求后的第一件事是分级，两级需求走不同流程：

- **简单需求 → 快速通道**：作为单一任务直接进入工作流程执行，免结构化提问、免任务包确认单、免任务拆解与清单落盘。
- **复杂需求 → 完整流水线**：`需求校验 → 任务拆解 → 任务包确认（必要时）→ 任务清单落盘 PROGRESS → WIP = 1 逐任务执行 → 归一收尾`。

#### 简单需求判定标准（缺一不可）

- [ ] **修改范围很小**：改动集中在当前模块的 1~2 个文件、少量代码行内。
- [ ] **只影响当前模块**：不跨模块协同，不改公共代码（公共工具函数、schema、provider、全局配置）。
- [ ] **不是新增功能面**：无新命令、新交互步骤、新工具、新接口、新数据流，只是对既有功能的小修小补（如改一个字段名、调整提示文案、修正注释或笔误）。
- [ ] **实现方式唯一**：无技术方案分歧，不需要用户在多个方案间做选择。
- [ ] **无高风险操作**：不涉及删除文件、修改公共依赖、数据库表结构等高风险变更。

#### 快速通道不减的底线

- 工程不变量校验照常执行（`bun run typecheck`、`bun run lint` 及 `bun run test`）。
- 遇到 Bug / 报错仍按 `docs/bug-fix-guide.md` 执行。
- 文档同步按需精简：不涉及结构 / 业务逻辑变更（如纯文案、注释修正）可跳过 `ARCHITECTURE.md`；涉及结构 / 业务逻辑的仍必须同步。
- 原子提交规范不变。

#### 回退机制

- **拿不准就不走快速通道**：任一条判定标准存疑，一律按复杂需求执行完整流水线。
- **执行中升级**：若发现实际影响面超出预期（如字段名被多处引用、牵出联动逻辑），**立即停止编码**，回到需求校验环节补齐任务包确认单并经用户确认后再继续。

凡不满足简单需求任一判定标准的，一律视为**复杂需求**：跨模块、多文件改动、新增功能面、存在方案分歧或高风险操作的需求都属此类，必须走第 3~5 节校验与任务拆解，并按工作流程第 2~4 步执行任务清单落盘与 WIP 执行。

### 3. 校验维度清单

复杂需求在接收后，请默念并逐一校验以下 5 个维度。若任何一项不明确，需向用户确认：

#### 维度一：目标与范围界定

- [ ] **核心目标**：用户是否清晰表达了“为什么做”以及“期望的最终结果是什么”？警惕“优化一下”、“改好点”等模糊词汇，必须追问具体指标或现象。
- [ ] **影响范围**：根据 `ARCHITECTURE.md` 和模块划分，该需求涉及哪些具体的模块？
- [ ] **越界检查**：是否明确说明了“不需要改什么”（Out of Scope）？防止 Agent 在重构时引发连带故障。

#### 维度二：多模块协同策略 [重要]

当需求涉及 2 个或以上模块的修改时，必须明确执行策略与隔离方案：

- [ ] **执行顺序**：是串行依赖（必须先改 A 模块才能改 B 模块），还是并行独立（A 和 B 互不影响）？
- [ ] **原子性拆解**：多模块需求必须拆解为可独立验证的细分任务（见第 5 节任务拆解规则），并明确串行依赖与中间状态。细分任务完成后更新 `PROGRESS.md` 状态；整项需求完成后统一提交。只有多个需求彼此独立、具备单独交付价值时才拆成多个 Commit。
- [ ] **文档所有者**：跨模块业务闭环必须指定唯一主层级目录（本项目为仓库根目录，或已建立模块文档的模块目录，当前为 `apps/agent/src/workflows/`），作为 `ARCHITECTURE.md`、`PROGRESS.md` 和按需 `DECISIONS.md` 的文档所有者；其他层级 / 模块只记录指向主文档的索引。
- [ ] **状态一致性**：中间状态如何保证系统不崩溃？例如：新旧接口字段不兼容时，是否需要兼容性代码？

#### 维度三：验收标准与不变量

- [ ] **功能验收**：给定什么输入，期望什么输出？边界情况（如空数据、超长文本）如何处理？
- [ ] **联动清单（重要）**：需求涉及多个联动的状态（如 Agent 工具调用与上下文状态联动、配置项驱动行为切换、流式输出与中断处理）时，**必须**逐一列出联动关系：A 变化时 B/C 如何响应？旧状态是否清空、是否回退默认值、空数据时保持什么状态？遗漏任一支路即视为需求不完整，须当场向用户确认。
- [ ] **工程不变量**：本次修改是否需要满足特定的性能指标、类型检查或测试覆盖率？

#### 维度四：上下文与资料补全

- [ ] 用户是否提供了必要的参考文件路径、设计稿链接或 API 文档（如所用 LLM 服务商的接口文档）？
- [ ] 如果需求涉及历史遗留代码，用户是否说明了已知的坑（如“不要动 utils 里的时间格式化函数”）？

#### 维度五：风险与决策记录

- [ ] 如果实现该需求有多种技术方案，是否需要向用户列出利弊并让其选择？
- [ ] 涉及高风险操作（如修改数据库表结构、删除核心文件、引入新的外部依赖），是否已提醒用户并等待确认？
- [ ] **决策落盘**：本次需求是否产生了重大决策（需 Human-in-the-loop 介入的方案选择、高风险操作确认、架构取舍等）？若有，是否已将决策信息追加到对应层级的 `DECISIONS.md`（本项目当前放仓库根目录，与项目级状态文档同级；不存在则创建）？

### 4. 交互规范

当发现需求不完整时，请遵循以下交互规范：

1. **不要连环问**：将同类问题合并，一次性向用户提出最多 3 个核心问题。
2. **提供选项而非填空**：尽量基于代码库现状给用户提供选项。例如：“该需求涉及 Agent 核心循环和工具模块，请问是先定核心循环的接口（A），还是先实现工具注册表并提供 Mock（B）？”
3. **给出你的建议**：作为高级工程师，在提问时附带你的最优解建议。

### 5. 任务拆解与任务包确认单

复杂需求澄清后、开始编码前，必须先对需求做**任务拆解**，再输出包含任务清单的**《任务包确认单》**。方案唯一且无高风险的复杂需求，确认单兼作执行摘要，输出后可直接开始；存在需确认事项（歧义、方案分歧、多模块顺序、高风险操作）时，须等待用户回复“确认”或“开始”。简单需求免此步骤。

**任务拆解规则：**

- 将需求拆解为多个可独立验证的细分任务，构成**任务清单**；粒度以「一个细分任务 ≈ 一次状态更新与闭环校验」为宜。
- 每个细分任务必须写全四要素：
  - **完成状态**：`未开始 / 进行中 / 已完成`，初始均为 `未开始`；
  - **主要业务目的**：该任务交付什么业务价值、为什么需要它；
  - **完成判断条件**：可执行的验证点（整体 AC 的分解，含边界情况）；
  - **涉及模块**：具体到模块目录或公共代码位置。
- 多模块需求的任务顺序遵循维度二的执行顺序结论（串行依赖先 A 后 B；并行独立可任意顺序，但同样逐个执行）。

**任务包模板：**

```text
【任务包确认单】
- 目标：[一句话描述目标]
- 需求分级：复杂需求（不满足快速通道判定：[简述原因]）
- 涉及模块：[模块A, 模块B]
- 执行策略：[如：串行执行，WIP=1，细分任务完成后更新 PROGRESS 状态，整项需求完成后统一提交]
- 任务清单：
  1. [任务名]｜状态：未开始｜业务目的：[...]｜完成判断条件：[...]｜涉及模块：[...]
  2. [任务名]｜状态：未开始｜业务目的：[...]｜完成判断条件：[...]｜涉及模块：[...]
- 验收标准(AC)：
  1. [具体的可执行验证点]
  2. [边界情况处理]
- 不做范围：[明确排除的内容]
存在需确认事项时，请回复“确认”或“开始”。
```

## 工作流程

在执行任何代码修改任务时，必须严格遵循以下标准化的工程流水线，确保系统状态的一致性与可追溯性：

### 1. 上下文加载与状态感知

- 读取状态文档 `ARCHITECTURE.md` 获取架构蓝图，明确文件职责与依赖边界。文档分两级：项目级在仓库根目录；需求落在已建立模块文档的目录（当前为 `apps/agent/src/workflows/`）时，同时读取该模块目录内的文档。
- 读取状态文档 `PROGRESS.md` 获取最新进度，特别关注“已知 Bug”区域，避免踩历史坑（读取层级同上）。
- **断点续作检查（重要）**：若 `PROGRESS.md`「进行中」区域存在未完成的任务清单，说明上一需求被中断（用户中断、会话结束或不可抗原因）。此时**优先**向用户确认是否从清单中第一个未完成的任务恢复执行；未澄清前不得开启新需求覆盖清单。
- *注：目录已存在但文档缺失时视为存量模块，按本次修改逐步补齐；只有业务模块目录本身不存在时才视为新建模块。*

### 2. 任务清单落盘（复杂需求，编码前）

任务包确认（或执行摘要输出）后、正式编码前，必须把当前需求与任务清单写入主涉及层级的 `PROGRESS.md`「进行中」区域（层级判定同第 1 步：项目级在仓库根目录，需求落在已建立模块文档的模块目录时为模块级；跨模块需求写主模块，其余模块的 `PROGRESS.md` 记一条指向主清单的索引）：

```markdown
### 进行中：[需求名]（YYYY-MM-DD 拆解）

- [ ] 任务 1：[任务名]｜涉及模块：[...]｜业务目的：[...]｜完成判断条件：[...]（状态：未开始）
- [ ] 任务 2：[任务名]｜涉及模块：[...]｜业务目的：[...]｜完成判断条件：[...]（状态：未开始）
```

**落盘目的**：复杂需求一旦中断（用户中断、会话结束或不可抗原因），下一个对话 / Agent 可凭清单无损接续（见第 1 步断点续作检查）。任务清单归属于当前父需求，是执行期的「断点存档」，不是独立的历史完成记录。

### 3. 逐任务执行（WIP = 1）与闭环校验

- **WIP = 1（复杂需求）**：一次只做**一个**拆解任务。当前任务未达到其完成判断条件并通过下列校验前，禁止开始下一个任务。
- **完成一个，更新一次（复杂需求）**：开始一个拆解任务时，先将清单中该任务状态改为`进行中`；该任务闭环通过后，**立即**在 `PROGRESS.md` 清单中勾选复选框、状态改为`已完成`，然后才进入下一个任务。拆解任务完成不单独 commit；当前父需求完成并统一验收通过后，才按第 4 步将任务清单归一为一条完成记录，再将代码与文档作为一次原子提交落盘。
- 按照需求规范编写代码，严格遵守技术约束（不越界修改、不引入未授权依赖）。
- **静态校验**：执行工程不变量校验（`bun run typecheck`、`bun run lint` 及 `bun run test`）。
- **运行时校验（重要）**：本项目为纯后端/CLI 应用（无 UI），**禁止**仅凭静态校验通过即判定完成——必须通过可执行的方式实际验证一次：优先将受影响的行为写成单元测试（`bun:test`），或直接运行受影响的入口/函数（如 `bun run dev`、REPL、`curl` 调用本地服务）观察实际返回。尤其要覆盖维度三列出的「联动清单」每一条支路，以及空数据 / 边界场景。静态校验只能保证「代码能编译/符合规范」，无法保证「逻辑跑得通」。
- **无法运行时验证时**：必须记录未验证项、阻塞原因、已执行的替代验证和建议的人工复验步骤。本项目典型场景是涉及真实 LLM 调用而无法自动验证的路径——须向用户列出具体验证步骤并请用户操作反馈。
- **闭环修复**：若静态或运行时校验报错，必须捕获错误日志并交由 Agent 自我修复。此过程循环进行，直到所有校验 100% 通过。若工程存在与本次修改无关的历史遗留告警，以任务开始时记录的检查基线为准：历史问题不阻塞，但本次修改不得新增错误。**禁止带着本次修改产生的报错进入下一步**。

简单需求作为单一任务执行本步骤，无任务清单与逐任务状态更新，其余校验要求一致。

### 4. 文档同步与状态落盘

代码校验通过后，必须立即同步更新对应层级的文档（项目级在仓库根目录，模块级在模块目录内），保证代码与文档的原子性一致：

- **清单归一（复杂需求，收尾必做）**：任务清单全部完成、整个需求通过验收后，将 `PROGRESS.md`「进行中」区域的任务清单**整体删除**，归一为一条完成总结（时间、需求目标、改动范围、验收结果）写入「已完成」区域。完成总结落盘后，方可进入提交步骤；未完成任务及其清单不得进入历史记录。
- **更新 `AGENTS.md`（入口文档同步）**：本次修改若属于重大变更（新增目录或模块、调整模块职责与边界、技术栈变动等会影响项目整体认知的内容），**必须**同步更新项目入口文档 `AGENTS.md` 的「目录结构与模块划分」等对应章节，保持入口文档与项目实际结构一致。
- **更新 `ARCHITECTURE.md`**：
  - 新增功能：补充新特性、文件结构或数据流向说明。
  - 变更旧功能：**必须删除**旧功能的相关描述，替换为新的实现逻辑，保持文档与代码的绝对一致。
- **更新 `PROGRESS.md`**：
  - 在“已完成”区域追加本次修改的时间（格式统一为 `YYYY-MM-DD`）、类型、修改范围及关联的验收标准 (AC)。
  - 已完成区域只保留最近 5 条已完成需求的完成总结；只有新增完成总结导致超过 5 条时，才将最旧的完成总结合并进「历史归档」中的一条滚动摘要（更新摘要时间范围、涉及模块和关键主题），不新增逐任务历史条目。进行中需求及其任务清单、待办需求和已知 Bug 不参与压缩，也不得进入历史记录。
  - 若修复了历史遗留 Bug，需将其从“已知 Bug”区域移除。
  - 若引入了新 Bug 或未完成部分，需如实记录在对应区域。
- **追加 `DECISIONS.md`（重大决策落盘）**：
  - 本次需求若产生了重大决策（需 Human-in-the-loop 介入的方案选择、高风险操作确认、架构取舍等），**必须**将决策信息追加到对应层级的 `DECISIONS.md`（本项目当前放仓库根目录）。
  - 对应层级若**不存在** `DECISIONS.md`，则**先创建**该文件再追加。
  - 记录“为什么”而非“做了什么”：决策背景、备选方案、权衡依据与最终结论。

### 5. 原子提交

- 将代码修改与文档更新作为一个完整的逻辑事务，执行 Git Commit（提交规范见 `docs/git-commit-guide.md`）。复杂需求的拆解任务不单独提交，整个需求归一落盘后统一提交；仅当本次同时交付多个彼此独立、具备单独交付价值的需求时，才拆成多个 Commit。确保仓库始终处于一致、健康的状态。
