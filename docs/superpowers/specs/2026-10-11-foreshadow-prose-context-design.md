# 章节正文生成伏笔上下文注入 设计规格

> 状态：**已确认**（2026-10-11——两项决策经用户确认：①伏笔进正文生成上下文为必做需求，登场伏笔仅注入伏笔卡片（用户提出）；②回收伏笔的登场章上下文 = 正文优先 + 概述兜底 + 预算护栏（三选项中用户选定）。设计全文经用户确认后开始执行。）
> 需求来源：用户提出——生成正文时需要读取当前章节已绑定的伏笔内容：登场伏笔仅读取伏笔内容；回收伏笔除伏笔本身外，还需读取其登场章内容（读概述还是正文经讨论定为分层策略）。
> 前置依赖：write-chapter 章节正文生成链路已成熟（prompt 组装点单一、无确认门、store 注入式测试替身惯例）；伏笔绑定字段（`appearChapterId` / `recoverChapterIds`）已由大纲/章节规划/手动编辑三路径落库；`output/document-writer.ts` 已有 `readDocumentArtifact(relativePath, dir): string | null` 读取原语（文件缺失返回 null，query CLI 读正文即用它）；`workflows/foreshadow-intake.ts` 已有 `buildChapterOrder` 全局章序（部 sort→幕 sort→章 sort）。

## 1. 背景与问题

当前 write-chapter 的写作上下文**不含伏笔**（世界观 / 角色摘要 / 部幕概述 / 本章概述 / 同幕前后章概述 / 参考文风），伏笔对正文的影响只经「章节概述」间接传导：章节规划时模型把伏笔表面行为写进概述，正文再扩写概述。这带来三个问题：

1. **显隐失控**：正文对伏笔的体现完全依赖概述转述，注意度（1 易发现→10 难发现）、埋线方式等伏笔卡上的结构化约束没有直接进入写作面；
2. **不一致向未来传播**：用户编辑伏笔后，未写章节的正文会顺着冻结的旧概述跑偏——伏笔设定更新对「未来」不生效；
3. **回收无从呼应**：回收章看不到登场章的实际呈现（那把「契诃夫之枪」具体挂在哪面墙、用了什么措辞），回收容易写得空泛或与登场细节矛盾。

本需求把「绑定到本章的伏笔」注入正文生成上下文，一次性消解 ①③，并把 ② 缩小为「只剩已写正文不一致」（那部分由后续的一致性机制处理，见第 7 节）。

## 2. 用户确认的决策

1. **伏笔进正文生成上下文（必做）**：每次生成正文时读取当前章绑定的伏笔——
   - **登场伏笔**（`appearChapterId` = 本章）：仅注入伏笔卡片内容，不注入其他章内容（本章就是种下之地，卡片即全部所需）；
   - **回收伏笔**（`recoverChapterIds` 含本章）：注入伏笔卡片 + 登场章上下文 + （多步回收时）既往回收章概述。
2. **登场章上下文 = 正文优先 + 概述兜底 + 预算护栏**（正文 / 概述 / 全文无预算三选项中选定）：
   - 正文是**读者实际读到的最终事实**——概述只是规划骨架，正文里的具体呈现（场景、措辞、物件）只存在于正文；且正文文件可被用户直接手改（文件系统存储的既定用法），文件才是事实源；
   - 概述兜底覆盖「登场章已规划未写」「正文文件缺失/被移走」两类场景；
   - 预算护栏保护小上下文写作模型（写作模型是任意 OpenAI 兼容端点，可能是本地小模型），超预算降级为概述并 notify。
   - 否决「仅概述」：回收呼应感弱，存量老章与手改正文的具体细节丢失；否决「全文无预算」：一章回收多条伏笔时 prompt 膨胀 6~9k+ 字符，小上下文模型有溢出风险；否决「LLM 预提取相关片段」：非确定性、每条多一次调用，违背本项目确定性组上下文惯例。

## 3. 详细设计

**零 schema 迁移**：本需求纯 workflows 层 prompt 组装改动，无表结构、无契约、无协议变更。

### 3.1 伏笔读取与分组（write-chapter.ts 上下文组装处）

- `WriteChapterOptions` 增 `foreshadowStore?: ForeshadowStore`（缺省 `getDefaultForeshadowStore()`，测试注入替身，对齐既有 store 注入惯例）。
- `listForeshadows(novelId)` 全量行内存过滤为两组（伏笔量级为每本十几条，无需新 SQL 方法）：
  - **登场组**：`foreshadow.appearChapterId === chapterNodeId`，按入库顺序；
  - **回收组**：`foreshadow.recoverChapterIds?.includes(chapterNodeId)`，按**登场章全局章序升序**排（`buildChapterOrder` 复用——更早埋设的优先保正文预算），登场章不可解析的排最后。
- **同章种收**（`appearChapterId` = 本章且 `recoverChapterIds` 含本章）：归回收组，标注「登场于本章」，不注入任何章内容。

### 3.2 回收组的登场章上下文解析（每条，依序判预算）

兜底链（确定性，无 LLM）：

1. `outlineStore.getOutlineNode(appearChapterId)`——按 ID 直查、不过滤版本，**归档旧版登场章照常解析出章名**（documents 全量含归档章正文，照读）；节点不存在（数据异常）→ 该条不注入章上下文，标注「（登场章信息不可用）」，不阻塞生成；
2. `documentStore.getDocumentByChapter(appearChapterId)` 有行 → `readDocumentArtifact(filePath, outputDir)` 读正文：非 null → 注入**登场章正文**；null（文件缺失/被移走）→ 兜底概述；
3. 无 documents 行（登场章已规划未写）→ 兜底**该章节点的 summary**（prompt 内标注「该章正文未生成，以下为剧情概述」；summary 为 null 的旧数据 → 占位「（该章无概述）」）。
4. **多步回收**：`recoverChapterIds` 中按全局章序排在**当前章之前**的其他回收章 → 注入其**概述**各一行（让模型知道已揭示到哪一步，防重复揭底；既往回收步不注入正文——承接需要事实清单，呼应才需要具体细节）。

**预算护栏**：常量 `FORESHADOW_PROSE_BUDGET = 8000`（字符，仅计登场章**正文**注入量；概述兜底不计——概述本就短）。按回收组顺序逐条判断：剩余预算容纳该条正文（整条，**不截断**——截断会切掉关键细节）则注入并扣减，否则该条降级为概述；后续条目继续用剩余预算判断（可能为 0，全部降级）。降级条数并入 notify 通报。

### 3.3 prompt 注入格式

位置：**【下一章】块之后、【参考文风】段之前**——伏笔是核心叙事上下文（与部/幕/章概述同区），长样本文风仍留在尾部（既有「不推远核心上下文」决策不动）。结构：

```
【本章伏笔】
一、本章登场（按「表面行为」自然融入剧情，严禁点破隐藏真相；注意度 1=读者容易察觉 → 10=极难察觉）：
1. 表面行为：<surfaceAction>
   隐藏真相（仅供把握分寸，本章不得点破）：<hiddenTruth>
   注意度：<N>/10
   埋线方式：<plantingMethod>（有则显示）
   创作目的：<purpose>（有则显示）
   服务角色：<名字1>、<名字2>（characterIds 经 characterStore 解析名字，有则显示；未匹配兜底原 ID，对齐客户端惯例）

二、本章回收（揭晓「隐藏真相」，须与登场时的具体呈现呼应，不复述原文）：
1. 登场于《<登场章名>》：表面行为：<surfaceAction> / 隐藏真相：<hiddenTruth>（注意度 <N>/10[，服务：名字…]）
   [既往回收：《<章名>》——<概述>（多步回收时逐行）]
   登场章正文（呼应其细节，不要照抄）：
   <登场章正文全文>
   （兜底时替换为：登场章正文未生成——该章剧情概述：<summary>）
```

- **写作要求条件附加**（仅有伏笔时，编号顺延既有清单）：登场伏笔按注意度控制显隐程度、自然带出不刻意；回收伏笔呼应登场章的具体细节、不复述登场原文。
- **notify**（生成前，对齐「🖋️ 本次参考文风」透明惯例）：`🔮 本章伏笔：登场 N 条、回收 M 条（X 条登场章正文缺失或超预算，以概述代替）`——X 为未生成/文件缺失/预算降级三类合计，为 0 时省略括号段。
- **零伏笔零注入零通知**：本章无绑定伏笔时 prompt 与 notify 与现状逐字节一致（对齐文风注入先例），不新增任何前置校验（伏笔是可选增强，不阻塞生成）。

## 4. 数据流

1. 用户点章卡「✍️ 生成本章正文」→ writeChapter 前置校验（不变）→ 上下文组装时新增读伏笔全量行、过滤登场/回收两组；
2. 回收组逐条解析登场章上下文（getOutlineNode → getDocumentByChapter → readDocumentArtifact，预算内注入正文、否则概述兜底）+ 既往回收章概述；
3. 拼 prompt（【本章伏笔】块插入【下一章】与【参考文风】之间）→ notify 伏笔名单 → 写作模型单轮生成 → 落盘入库（既有链路零改动）。

## 5. 错误处理

- 伏笔 JSON 列损坏（`parseJsonArrayColumn` 抛可读错误）：中止生成、协议入口转 fatal error——既有读路径行为，不新增处理；
- 登场章节点不存在：该条只注入卡片 + 「（登场章信息不可用）」标注，不阻塞；
- 正文文件缺失：静默兜底概述（并入 notify 计数），不告警不阻塞；
- `NOVEL_OUTPUT_DIR`：`readDocumentArtifact` 的 dir 参数与既有落盘一致取 `outputDir`（协议模式下宿主传绝对路径，读写同源）。

## 6. 测试计划（bun:test，FakeChannel + mock model + 临时库，对齐 write-chapter 既有测试形态）

- 无伏笔：prompt 无【本章伏笔】段、notify 无 🔮 行（现状回归，逐字节断言）；
- 登场伏笔：卡片全字段注入（含可选字段缺省省略、服务角色名解析）；
- 回收 + 登场章有正文：正文全文注入；
- 回收 + 登场章未写：概述兜底 + 「正文未生成」标注；
- 回收 + 文件缺失（有 documents 行、删文件）：概述兜底 + notify 计数；
- 多步回收：既往回收章概述注入且**不含**当前章之后的回收章；
- 预算：构造超长正文验证按登场章序降级、notify 条数、不截断；
- 同章种收：「登场于本章」标注、无章内容注入；
- 归档登场章：章名可解析、正文照读；
- 服务角色未匹配：兜底原 ID。

## 7. 不做范围（Out of Scope）

- **设定一致性机制**（编辑伏笔/角色的影响面弹框、「待同步」标记、正文重写/章节重规划阶梯）——本规格是「设定与已生成内容一致性」系列讨论的第一块；一致性机制与角色侧策略（含「角色不能改名」的落地）为后续独立讨论与规格。本需求落地后，**伏笔编辑对未写章节即滚动生效**，剩余不一致收敛为「已写正文」；
- 章节规划会话的伏笔注入（已有 `listUnboundByAct` / `listUnrecoveredByAct` 回传机制，与本需求不重叠）；
- 地点注入正文生成上下文（地点与章节无结构化绑定，另议）；
- CLI 终端创作流适配（write-chapter 本就无 CLI 交互入口，仅 headless 会话）。
