# 正文修订复用写作对话与缓存

状态：用户在调研结论后明确要求「按照这个建议的方案开始实施」，据此执行，无需重复确认。

## 目标与方案

原实现每轮重拼「资料 + 最新正文 + 最新报告 + 要求」，在初稿请求中间插入修订材料，第三轮又替换正文。改为一章一次会话内持续追加 SDK `ModelMessage[]`：首条 user 原样保留全部资料及写作要求，每次生成后追加 `result.response.messages` 原生结果；不通过时追加一条 user 审校报告及仅修订最新稿的要求。历史消息不 trim、不摘要、不重建；仅用于审校和最终落盘的正文沿用 trim。

独立审校模型、三段独立调用、最多三轮、最后一轮保底保存、空正文及调用异常零落盘、重生成失败保护旧正文均保留。报告作为外部编辑意见进入写作对话，不把审校器的对话并入写作者。

## 缓存与诊断

写作调用使用 canonical `providerOptions.anthropic.cacheControl = { type: "ephemeral" }` 启用 Claude 默认 5 分钟自动缓存；OpenAI/DeepSeek 适配器忽略其他厂商命名空间，继续使用服务自身自动缓存。首条完整请求始终不变，不调整 SDK/模型/公共协议/数据库。

新增工作流可选 `onUsage` 回调：每次成功写作调用返回小说、章、轮次、drafting/revising 阶段、模型/provider、durationMs、输入/输出与缓存读写 token。供应商未提供的数据记 null，不编造为零，不估算费用。headless 在 stderr 输出带固定事件类型的单行 JSON，stdout 协议与 UI 提示保持原有语义；不记录 API Key、请求正文、报告或模型原始载荷。

## 验收

1. 第 2/3 次写作请求严格保留旧请求全部消息，只追加原生 assistant 结果和当前报告；正文空白、reasoning/provider 元信息保真，提示明确针对最新稿。
2. 初稿资料与要求、审校上下文和落盘行为回归通过；第三轮后无第 4 次生成。
3. 真实 SDK + 临时 SQLite + HTTP 边界替身覆盖三种 provider 的三轮写作，审校独立；Claude 实际 HTTP 请求有 cache_control，其他协议无该字段；用量回调反映 SDK 数值与缺省 null。
4. headless 诊断只在 stderr，stdout 每行仍过 shared 协议验证；无正文/Key 泄漏。
5. `bun run typecheck`、`bun run lint`、`bun run test` 通过。真实服务缓存命中、账单与耗时收益需线上测量，本地替身不证明这些收益。

## 权衡与边界

追加历史增大逻辑上下文和网络载荷，但有利于复用完整缓存边界。当前最多初稿加两次修订，因此不加入压缩或截断；保留历史不保证命中缓存或降低总费用。Claude 默认 TTL 不覆盖长时间生成及审校时，可能重建缓存，不擅自改成额外收费的一小时缓存。不实现跨会话持久化或恢复，不更改审校 prompt。
