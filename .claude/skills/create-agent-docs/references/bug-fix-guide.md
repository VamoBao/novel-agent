# 缺陷与执行错误修复指南

> **模板适配说明**（落盘前删除本块）：本模板中的静态检查与测试命令为前端 TS 项目示例。落盘前请替换 `{{STATIC_CHECK_CMD}}`、`{{TEST_CMD}}` 占位符为项目实际命令；若用户不需要测试，删除测试相关内容。

## 1. 核心原则：先归因，再修复，后反思

在开发过程中遇到 Bug、报错或流程异常时，**严禁盲目尝试修改代码（如胡乱添加 try-catch 或随意改变逻辑）**。
Agent 必须首先进行**根因分析**，明确错误来源，并根据来源采取不同的修复与复盘策略。

## 2. 错误归因分类

捕获到错误后，请判断错误属于以下哪一类：

- **类别 A：技术实现与业务逻辑缺陷（非流程错误）**
  - 语法/类型错误（如类型检查报错、Lint 违规）。
  - 纯代码逻辑错误（如死循环、空指针引用）。
  - 产品交互与需求不符（如 UI 交互与设计稿不一致、接口字段处理错误）。
- **类别 B：工作流程引起的缺陷（流程错误）**
  - 因未充分阅读 `ARCHITECTURE.md` 导致文件放错目录或破坏了已有架构。
  - 因需求校验阶段漏问了边界条件，导致生成的代码缺少关键逻辑。
  - 因未遵循“原子提交”或“闭环校验”规范导致的中间状态崩溃。

## 3. 修复策略

### 针对类别 A：常规技术修复

按照标准的闭环修复流程处理：

1. **分析报错日志**：提取关键错误堆栈或异常现象。
2. **定位代码**：找到引发错误的具体文件与函数。
3. **实施修复**：编写正确的逻辑，确保不引入新的副作用。
4. **闭环校验**：重新执行 `{{STATIC_CHECK_CMD}}`（及 `{{TEST_CMD}}`，若项目启用测试），直到 100% 通过。

### 针对类别 B：流程修复与体系进化 [重要]

此类错误不仅是代码问题，更是工作流的漏洞。必须按以下三步处理：

1. **临时修复**：先将当前代码修复至可用状态，确保任务能继续推进。
2. **流程复盘与总结**：将复盘要点记录到 `PROGRESS.md` 本次任务条目下（勿只依赖会话内记忆，确保任务结束前不丢失）：
   - 产生的错误是什么？
   - 是因为工作流程中的哪一个步骤缺失或执行不到位导致的？
   - **优化方案**：为了防止未来再次发生，应该在哪个指引文件（如 `docs/feature-check-guide.md`）中增加什么具体步骤或约束？
3. **更新进度文档**：若该流程错误导致了明显的系统隐患，需在 `PROGRESS.md` 的“已知 Bug”或相关记录中如实标注。

## 4. 任务收尾与流程升级提醒

当本次需求的所有功能与 Bug 修复全部完成，准备提交最终代码前，若在本次任务中产生了**“类别 B（流程错误）”**的复盘记录，**必须**在最终输出中向用户发起流程升级提醒。

**提醒格式规范：**
> 💡 **流程优化建议**
> 在本次任务中，我发现了一个由于工作流程不足导致的问题：
>
> - **发生现象**：[简述遇到的错误，如：因未确认分页类型导致列表渲染崩溃]
> - **根因分析**：[如：`docs/feature-check-guide.md` 的需求校验清单中，未强制要求确认接口是偏移量分页还是游标分页]
> - **优化方案**：[如：建议在 `docs/feature-check-guide.md` 的「维度三：验收标准与不变量」中，增加一条“必须明确接口分页机制及边界处理”]
>
> 请问是否需要我将此优化方案追加到对应的指引文件中？（回复“是”则自动执行修改）

只有当用户明确回复“是”时，方可修改对应的 Markdown 指引文件；若用户拒绝或忽略，则按正常流程结束当前任务。
