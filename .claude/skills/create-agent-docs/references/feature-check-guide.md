# 需求指南

## 概述

- 用户提供的需求可能是模糊不完整的，需要对需求进行拆解评审，通过推荐或者用户回答的方式来完善需求的细节

> **模板适配说明**（落盘前删除本块）：本模板中的静态检查、测试与运行验证命令为前端 TS 项目示例。落盘前请按适配结论替换 `{{STATIC_CHECK_CMD}}`、`{{TEST_CMD}}`、`{{DEV_CMD}}` 占位符；若用户不启用测试，删除所有测试相关内容；若用户选择手动提交，删除第 4 节「原子提交」，改为「完成后向用户汇报修改摘要，等待用户下达提交指令」。

## 需求完整性与可行性校验指引

### 1. 核心原则：不盲从，先对齐

当用户在 CLI 中提出修改或新需求时，**严禁**立即开始编写代码。你必须首先作为“需求分析师”，对用户输入的意图进行解构与校验。
如果需求存在模糊、遗漏或执行风险，你必须向用户发起**结构化提问**，直到需求满足完整的交付标准后，方可进入开发阶段。

### 2. 校验维度清单

在接收需求后，请默念并逐一校验以下 5 个维度。若任何一项不明确，需向用户确认：

#### 维度一：目标与范围界定

- [ ] **核心目标**：用户是否清晰表达了“为什么做”以及“期望的最终结果是什么”？警惕“优化一下”、“改好点”等模糊词汇，必须追问具体指标或现象。
- [ ] **影响范围**：根据 `ARCHITECTURE.md` 和路由定义，该需求涉及哪些具体的模块？
- [ ] **越界检查**：是否明确说明了“不需要改什么”（Out of Scope）？防止 Agent 在重构时引发连带故障。

#### 维度二：多模块协同策略 [重要]

当需求涉及 2 个或以上模块的修改时，必须明确执行策略与隔离方案：

- [ ] **执行顺序**：是串行依赖（必须先改 A 模块才能改 B 模块），还是并行独立（A 和 B 互不影响）？
- [ ] **原子性拆解**：基于 ACID 原则，多模块需求必须拆解为多个独立的 Git Commit 节点。需向用户确认：“我们是否分步进行？先完成 A 模块的接口并提供 mock，再开发 B 模块的 UI？”
- [ ] **状态一致性**：中间状态如何保证系统不崩溃？例如：新旧接口字段不兼容时，是否需要兼容性代码？

#### 维度三：验收标准与不变量

- [ ] **功能验收**：给定什么输入，期望什么输出？边界情况（如空数据、超长文本）如何处理？
- [ ] **联动清单（重要）**：需求涉及多个联动的 UI 控件（如下拉框级联、表单字段联动、路由参数驱动查询）时，**必须**逐一列出联动关系：A 变化时 B/C 如何响应？旧选中项是否清空、是否回退默认值、空数据时保持什么状态？遗漏任一支路即视为需求不完整，须当场向用户确认。
- [ ] **工程不变量**：本次修改是否需要满足特定的性能指标、类型检查或测试覆盖率？

#### 维度四：上下文与资料补全

- [ ] 用户是否提供了必要的参考文件路径、设计稿链接或 API 文档？
- [ ] 如果需求涉及历史遗留代码，用户是否说明了已知的坑（如“不要动 utils 里的时间格式化函数”）？

#### 维度五：风险与决策记录

- [ ] 如果实现该需求有多种技术方案，是否需要向用户列出利弊并让其选择？
- [ ] 涉及高风险操作（如修改数据库表结构、删除核心文件），是否已提醒用户并等待确认？
- [ ] **决策落盘**：本次需求是否产生了重大决策（需 Human-in-the-loop 介入的方案选择、高风险操作确认、架构取舍等）？若有，是否已将决策信息追加到目标模块目录内的 `DECISIONS.md`（不存在则创建）？

### 3. 交互规范

当发现需求不完整时，请遵循以下交互规范：

1. **不要连环问**：将同类问题合并，一次性向用户提出最多 3 个核心问题。
2. **提供选项而非填空**：尽量基于代码库现状给用户提供选项。例如：“该需求涉及用户模块和订单模块，请问是先开发订单模块的 API（A），还是先调通用户模块的 Mock 数据（B）？”
3. **给出你的建议**：作为高级工程师，在提问时附带你的最优解建议。

### 4. 输出标准：任务包确认单

当所有疑问澄清后，在开始编码前，你必须向用户输出一份精简的**《任务包确认单》**并等待用户回复“确认”或“开始”：

```text
【任务包确认单】
- 目标：[一句话描述目标]
- 涉及模块：[模块A, 模块B]
- 执行策略：[如：串行执行。先改模块A并Commit，再改模块B并Commit]
- 验收标准(AC)：
  1. [具体的可执行验证点]
  2. [边界情况处理]
- 不做范围：[明确排除的内容]
确认无误请回复“开始”。
```

## 工作流程

在执行任何代码修改任务时，必须严格遵循以下标准化的工程流水线，确保系统状态的一致性与可追溯性：

### 1. 上下文加载与状态感知

- 读取目标模块目录内的 `ARCHITECTURE.md` 获取架构蓝图，明确文件职责与依赖边界。
- 读取目标模块目录内的 `PROGRESS.md` 获取最新进度，特别关注“已知 Bug”区域，避免踩历史坑。
- *注：若文件不存在，视为新建模块，需在后续步骤中创建。*

### 2. 代码实现与闭环校验

- 按照需求规范编写代码，严格遵守技术约束（不越界修改、不引入未授权依赖）。
- **静态校验**：执行工程不变量校验（`{{STATIC_CHECK_CMD}}`，及 `{{TEST_CMD}}`，若项目启用测试）。
- **运行时校验（重要）**：本次改动若涉及 UI 联动、表单、路由跳转、异步状态切换等**运行时行为**，**禁止**仅凭静态校验通过即判定完成——必须通过可执行的方式实际验证一次：优先用测试脚本或直接调用受影响的接口/函数（如 `curl`、REPL、单元测试）观察返回；无法自动验证的交互行为（如切换下拉、提交表单），须向用户列出具体验证步骤，请用户在 `{{DEV_CMD}}` 启动的环境中操作并反馈结果。若项目无 UI（纯后端/库），则实际调用受影响的接口/函数并验证返回。尤其要覆盖维度三列出的「联动清单」每一条支路，以及空数据 / 边界场景。静态校验只能保证「代码能编译/符合规范」，无法保证「逻辑跑得通」。
- **闭环修复**：若静态或运行时校验报错，必须捕获错误日志并交由 Agent 自我修复。此过程循环进行，直到所有校验 100% 通过。**禁止带着报错进入下一步**。

### 3. 文档同步与状态落盘

代码校验通过后，必须立即同步更新对应模块的文档，保证代码与文档的原子性一致：

- **更新 `AGENTS.md`（入口文档同步）**：本次修改若属于重大变更（新增目录或模块、调整模块职责与边界、技术栈变动等会影响项目整体认知的内容），**必须**同步更新项目入口文档 `AGENTS.md` 的「目录结构与模块划分」等对应章节，保持入口文档与项目实际结构一致。
- **更新 `ARCHITECTURE.md`**：
  - 新增功能：补充新特性、文件结构或数据流向说明。
  - 变更旧功能：**必须删除**旧功能的相关描述，替换为新的实现逻辑，保持文档与代码的绝对一致。
- **更新 `PROGRESS.md`**：
  - 在“已完成”区域追加本次修改的时间（格式统一为 `YYYY-MM-DD`）、类型、修改范围及关联的验收标准 (AC)。
  - 若修复了历史遗留 Bug，需将其从“已知 Bug”区域移除。
  - 若引入了新 Bug 或未完成部分，需如实记录在对应区域。
- **追加 `DECISIONS.md`（重大决策落盘）**：
  - 本次需求若产生了重大决策（需 Human-in-the-loop 介入的方案选择、高风险操作确认、架构取舍等），**必须**将决策信息追加到目标模块目录内的 `DECISIONS.md`。
  - 模块内若**不存在** `DECISIONS.md`，则**先创建**该文件再追加。
  - 记录“为什么”而非“做了什么”：决策背景、备选方案、权衡依据与最终结论。

### 4. 原子提交

- 将代码修改与文档更新作为一个完整的逻辑事务，执行 Git Commit（提交规范见 `docs/git-commit-guide.md`）。确保仓库始终处于一致、健康的状态。
